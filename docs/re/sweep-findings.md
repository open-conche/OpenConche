## 1. `require` resolution

**Rule (fact, `_luaB_require` 0xc3134, stock Lua 5.0.2):**
1. Argument must be a string. `_LOADED` (registry-level table) is looked up by the **raw argument string**; if the entry is truthy, return it and stop (no re-run). `_LOADED` must be a table, else error.
2. Path = global `LUA_PATH` if it is a string, else env var `LUA_PATH`, else the built-in default `"?;?.lua"` (string at 0x15de40; Windows exe 0x5743b8).
3. Split on `;`. A leading `;` is skipped; an empty remainder ends the search. For each template replace **every** `?` with the argument verbatim and call `luaL_loadfile` (0xa5850). Status 2 (file not found / not openable) goes to the next template. Any other failure (e.g. syntax error) raises ``error loading package `%s' (%s)``. When the templates run out: ``could not load package `%s' from path `%s'`` (string at Windows 0x574400).
4. On success: save the old global `_REQUIREDNAME`, set it to the name, call the chunk with 0 args and 1 result, restore `_REQUIREDNAME`. If the result is nil store `true`. Store the result in `_LOADED[name]` and return it.
- There is **no `.lua` suffix logic**. `name` is tried exactly as given, so `"x.lua"` hits template `?` and `"x"` does not. `/` is not special: it is copied into the path. Each template result goes to the asset FS (`_pf_open` -> `TFile::Open`), which lowercases and maps names (`TFile::TranslateResource` 0x539e2); I found no extension fallback in `TFile::Open`/`ScanFolderForResources`. The only other `.lua` handling in the binary is `Content.c` (content.xml names), unrelated.
- The main state's `LUA_PATH` global is `?;../?;../../?` (prelude constant; `api-windows.md`). So the original's search list for `require("ui/foo.lua")` is `ui/foo.lua`, `../ui/foo.lua`, `../../ui/foo.lua` (all relative to the asset root; the `..` ones just fall off the FS and miss). The compile-state path `assets/?;../?;?` (0x15c498) is for `TScriptCode::Get` only. The `?;?.lua;scripts/?;...` string at 0x15c07c is not used by `require` (not traced further).
- **Consequence (fact + inference):** per this code, `require("ui/catalogue_history_documents")` (no `.lua`) fails in the original Mac engine with exactly the engine's message, because the file is `ui/catalogue_history_documents.lua`. The Windows exe has the same strings in the same order and the same default path, so it very likely behaves the same **(inference; I could not read the Windows code)**. Reforged does not patch the exe (README: "the original `chocolatier-decadence.exe`"), and no Reforged Lua assigns `LUA_PATH`, so I cannot explain how its History tab loads. Possible explanation: Reforged was only exercised with the History panel under a different path, or the Windows `TFile` layer differs **(unknown)**.
- Both callers are `ui/catalogue_history_detail.lua:8` and `ui/catalogue_history_document.lua:7`; the former is reached from `ui/catalogue_detail.lua:24` via `dofile`.

**What the engine should implement:** the faithful algorithm above (the engine's `?;../?;../../?` is already correct). Because Reforged's own Lua needs the bare name to work, add one deliberate, documented deviation: if every template fails and the name does not end in `.lua`, retry the templates with `name .. ".lua"`, keep `_LOADED` keyed by the original string, and `_REQUIREDNAME = name`. This only turns errors into successes, so it cannot change any behaviour of code that worked in the original. Do not strip or alter `/`.

## 2. `SaveCreationToFile`

- **Not a native anywhere (fact).** Not in the Mac binary (no string, no registration), not in `chocolatier-decadence.exe`, `CadiApi.dll`, `ddraw.dll`, `dsound.dll`, `Chocolatier Reforged.exe` (156 KB launcher) by string search (ASCII; I did not search UTF-16). Reforged runs on the unmodified original exe, so the call would hit a nil global.
- **Never executed (fact).** `ui/ui_kitchen.lua:1023` defines the global function `SaveCreation`, which builds `{name, description, category, ingredients = {ingredient names, in slot order, blanks skipped}, appearance = { {image, r, g, b}, ... up to 4 layers }}` and calls `SaveCreationToFile(table)` (line 1056). Nothing references `SaveCreation`: the Test Kitchen button at line 1107 is `load_creation` -> `LoadCreation` -> `OpenCommunityCookbook()` (a Lua function, `ui_kitchen.lua:877`). The real "share" path is `SaveSelectedCreation` in `ui/recipe_recipe.lua:34` (button `recipe_save_community`, label `save_creation`) -> `CommunityCreation.FromProduct` -> `ui/community_creation_upload.lua` -> HTTP via the Community Bridge (a separate Reforged helper exe talking over files/`community/transport.lua`). Neither the name, location nor format of a file exists; there is no return-value use.
- **Reader (fact):** nothing reads a file this function would write. The shape it passes matches `CommunityCreation.FromKitchenData` (`community/creation.lua:233`: adds `schema_version` 1 and `game_id` "c3_dbd", then `Normalize` checks name 1-100 bytes, description <= 400, category, known ingredient ids, <= 4 appearance layers with integer 0-255 RGB). `ToKitchenData` (line ~248) is the inverse used by the Cookbook import.
- **Engine action:** leave unregistered or register a logged no-op returning nothing. No file format is needed. Custom recipes persist inside the normal save (`Player` data), not via this call (`coffee-factory-and-recipes.md` section 3).

## 3. `CreditsWindow` (`TCredits`, `re/mac/decomp/TCredits.c`)

Lua: `ui/ui_credits.lua` builds a dialog (`image/popup_back_generic_tall`, name `credits`, x=1000 offscreen then `CenterFadeIn`) with `CreditsWindow{x=21,y=54,w=458,h=347, font=uiFontName, fontsize=16, fontcolor=BlackColor, headercolor=BlackColor, columngap=10, columnwidth=224, time=..., intropause=3000, file="credits.txt"}`, a `Text` for the version line, and an `ok` button (`default=true, cancel=true`, closes via `FadeCloseWindow("credits","ok")`).
Differences: vanilla `time=20000`, version `Text{label="#"..gVersionString}`, ok at y=424; Reforged `time=30000`, `label="gVersionString"` (no `#`, so a string-table lookup: `strings.xml` row `gVersionString` = "Chocolatier: Decadence by Design Reforged - v.2"), ok at y=410. Vanilla `gVersionString` = `"ver " .. config kGameVersion` (`api-globals.md`).

**Init (0x1b39e) (fact):** style ints `time`, `intropause`, `columngap`, `columnwidth` (default 0); strings `font`, `file`; number `fontsize`; colours `fontcolor`, `headercolor` (default white, converted to the 8-hex `rrggbbaa` string via `(int)(c*255)` each). Opens `file` through the asset FS (`_pf_open`), reads lines with `_pf_gets` (buffer 1024); the **last character of every line is dropped unconditionally** (assumes a trailing `\n`; a final line without `\n` loses a real character; **inference** the shipped files end with a newline).
Per line, three column strings are extended:
- Line contains `|`: split at the first `|`. Left part -> `CreditLine` into column A, right part -> `CreditLine` into column B, `"\n"` into the centre column C.
- No `|`: `"\n"` into A and B, `CreditLine(line)` into C.
- `CreditLine` (0xaf22): trim trailing then leading spaces/tabs; then copy chars, translating `[` to `<font color='RRGGBBAA'>` (the headercolor string) and `]` to `</font>`; append `"\n"`. Everything else, including other markup such as `<b>`, `<font size='20'>` and `&`, passes through verbatim to the rich-text parser (`fonts-and-text.md` 3). Blank lines become empty lines.
After the file ends, `floor(windowHeight / fontsize)` extra `"\n"` are appended to each column (347/16 = 21 blank lines) so the text scrolls fully out of view. Three `TTextGraphic`s are created with `Create(text, width, height=windowHeight, flags=1, font, fontsize, fontcolor)`: A and B are `columnwidth` wide (224), C is `2*columnwidth + columngap` (458) wide. `flags=1` is the TTextGraphic alignment flag for centred text **(inference from `fonts-and-text.md` 3.2: `flags & 1` = centre)**, so every column is centred. Then `startAnimation(0x10, ...)`: a per-frame task whose `OnTaskAnimate` just invalidates the screen.

**Draw (0x1be5e) (fact, re-traced):** the start time is latched on the first draw (`TPlatform::Timer`, ms). `e = now - t0`; `e' = 0` while `e < intropause`, else `e - intropause`. Scroll pixels `s = ((e' mod time) * H) / time` (unsigned integer mod and multiply, then float divide), where `H` is stored once in Init as `(int)(bottom of GetTextBounds(column A, 1.0) / 2)` (integer divide by 2 of the **bounds bottom**, not of the window or of the elapsed fraction; it is a plain scale, not a centring term).
- `TTextGraphic::GetTextBounds` (0x825ae) leaves top = `this+0xc + scale*this+0x5c` and bottom = `top + totalHeight*scale`. For `flags = 1` (no vertical-centre/bottom bits) `+0xc` and `+0x5c` are 0, so **bottom = total height = sum of line heights** of the whole column, including the 21 trailing blank lines. Only left/right are recomputed from the lines.
- A line's height is the max run size (`fonts-and-text.md` 2: the run size is the font `size` in px) plus any `<br pad>`; a line that consumed a `\n` counts as a normal line, so blank lines are `fontsize` tall (a line with no consumed characters at all would be 0, but `"\n"` is a consumed character; **inference**, not run). So for plain 16 px text, height = 16 * lineCount. `<font size='30'>`/`size='20'` lines are taller.
- Draw passes the first visible line as a float stored in `TTextGraphic+0x58`: `firstVisibleLine = s / fontsize` (`fontsize` = style `fontsize`, `this+0x48`). `TTextGraphic::Draw` (0x8293c) takes `floor` of it as a **line index** (it skips that many whole lines regardless of their pixel height) and shifts the first drawn line up by `frac * lineHeight(+0x44 = fontsize)` pixels. So the scroll is in line units: line index `s/fontsize`, with the sub-line part applied in pixels using `fontsize`, not the real height of that line. For uniformly 16 px lines this is exactly pixel scrolling.
- Rects (`TTextGraphic::Draw(TRect)` 0x16cef4 uses x = rect[0], y = rect[1], clip height = rect[3]-rect[1]): all columns use y = `-fontsize` (window-relative) and bottom `h + 2*fontsize` (so clip height = `h + 3*fontsize`); A: x = `columngap`, B: x = `w/2 + columngap/2`, C: x = `columngap` (the right edges, `w/2 - columngap/2`, `w - columngap`, are not used by the text layout, which wraps at the Create width).
- **Final formula:** `topLineIndexFloat = ((max(0, e - intropause)) mod time) * floor(totalTextHeightPx / 2) / time / fontsize`; line `floor(topLineIndexFloat)` is drawn at window y = `-fontsize - frac*fontsize`, following lines stack by their own heights. Each cycle is `time` ms and restarts at the top with no new intro pause.
- **Does one `time` period scroll the whole file? No (fact from the arithmetic).** At the end of a period `topLineIndexFloat = totalHeight / 2 / fontsize`. Vanilla `credits.txt` (99 lines of 16 px + 21 trailing blank lines = 120 lines, 1920 px): H = 960, end index 60.0; the window then shows lines 61 to about 85 of 99, so the last ~14 lines (the copyright block) are never reached. Reforged (110 lines, mixed 16/20/30 px; column A 2096 px, H = 1048, index 65.5) reaches about line 90 of 110. The roll jumps back to the top at `time` with the last part never visible. Our engine seeing "about the middle" is the top of the window (index 60, 65) not the bottom of the visible area (about 22 lines lower).
- Where the `/ 2` comes from is **not determined** by the binary: it is a single `idiv 2` of the bounds bottom in Init. **Inference:** it would be a compensation for a doubled line count, e.g. on a CRLF `credits.txt` (see below) every file line becomes line + empty line, and half of the doubled height is the whole file; but with the 21 extra blank lines even that leaves the top of the window at about 55 percent of the file at the end. The shipped files in this repo are LF only (no `\r`, trailing newline), so this is not what happens here.

**`_pf_gets` line ending rule (fact, from the Mac build's behaviour as reported):** `_pf_gets` stops at `\r` **or** `\n`. Since Init drops the last character of every returned line, a CRLF `credits.txt` reads on the Mac build as the line (the `\r` dropped) followed by an empty line (the `\n` alone, dropped to ""), i.e. double-spaced. LF files (both copies in this repo are LF, 99 and 110 `\n`, 0 `\r`) read normally.

**Input:** `TCredits` overrides no mouse/key handler, so clicks fall through (the window is not a button). Escape/Enter work through the Lua `ok` button (`default` and `cancel`), per `window-system.md` 6.x `TModalWindow::OnChar`. Click on the OK button -> `FadeCloseWindow("credits","ok")`.

**Vanilla file format (fact, the vanilla `credits.txt`, 99 lines, Windows-1252 bytes):** `<b>Big Splash Games</b>`, then sections `[Original Game Design]` followed by names, two-column lines `[Art Direction] | [Programming]` / `<name> | <name>`, copyright lines wrapped in `[...]`. **Reforged file (110 lines)** uses `<b><font size='30'>..</font></b>` / `size='20'` headers and aligns two columns with spaces in the centre column (no `|`), but still has some `[...]` lines near the end (header colour only; both colours are black so `[]` is just a tag with no visual effect).

**Unknown:** (a) why `H` is half the bounds (see Draw; the binary only shows the divide by 2; no Windows decompile of `TCredits` is in `re/win/decomp`, so whether the Windows build has the same `/2` is unverified). (b) Whether `TTextGraphic::Create`'s fourth parameter is only alignment. (c) Behaviour with a missing file: `_pf_open` returns 0, and the following `_pf_gets(0, ...)` is not guarded (probably crashes or returns 0 = empty credits; **unknown**). (d) What `startAnimation(0x10,...)` flags 'true,true,false' mean beyond per-frame callbacks (`game-windows-questions.md` 9.2 covers the arguments).

## 4. Escape and Rollover clicks

### 4a. Escape (fact)
No window flag and no `onKeyDown`. `TModalWindow::OnChar` (0x74d42) handles Enter and Escape for every modal: it walks the whole modal with `FindDefault::Process` (0x181170) to find a `default` and a `cancel` button, presses the one for the key via `TButton::DoCommand`, and if nothing was pressed (or `DoCommand` returned false) sends a `kDefaultAction` message to the focus window (or the modal). No Lua consumes `kDefaultAction`. The key is always consumed.
- A button qualifies only if the style flags `default`/`cancel` are set **and the button and every ancestor up to and including the modal have the enabled/visible bit 0x100**. So `EnableWindow(name,false)` (hide) disables the key binding. Traversal is forward over the child list; each match **overwrites** the previous (last match wins), and the walk stops as soon as both a default and a cancel have been found.
- So a dialog closes on Escape only if it has a visible `cancel=true` button whose command closes it. Mapping the four reported cases (Lua):
  - **Recipe book** `ui_recipes.lua`: `cancel` button exists (vanilla l.73, Reforged l.162) but is disabled via `EnableWindow("cancel", false)` (vanilla l.103, Reforged l.207) outside a selection picker (Reforged enables it at l.200 in picker mode). `ok` is `default` only. -> no close. Matches.
  - **`ui_colorselect`**: only colour swatch buttons, none `cancel`. -> no close. Matches.
  - **Quest offers** `ui_quest_offer.lua`: `reject` is `cancel=true`; `accept` is `cancel=okCancel` (true only when defer and reject are both `"none"`); `defer` is never cancel. A reject-less offer (defer + accept) has no cancel, so Escape does nothing; accept + reject: Escape = Reject (quest rejected!). Single accept: Escape = Accept.
  - **Crates** `ui_crates.lua`: button `done` (label "cancel", `cancel=true`, command `Cancel` = `CloseWindow`) is enabled during betting, so Escape closes then; after the bet, `done` gets `SetCommand("done", Finish)` and label "done" and stays `cancel=true`, so Escape runs `Finish` (reveal all) rather than closing; after that `done` is disabled and `close` (no `cancel`) is enabled, so Escape does nothing.
- **Engine comparison:** `ModalWindow::onChar` (`src/ui/Window.cpp:140`) implements the same scheme (finds `isCancel()` buttons, `visibleToModal` checks `shown()` up to the modal, falls back to `kDefaultAction` to the focus). Behaviour for the four cases should therefore match, provided the engine's `SetCommand` on the `done` button and `EnableWindow` are honoured. **One difference:** the engine picks the **first** matching button in pre-order (`findButton`); the original keeps the **last** match in forward child-list order (and stops once default and cancel are both found). Only visible when two enabled cancel buttons coexist, and I did not find such a dialog. Check child list order (front/back) before changing.

### 4b. Rollover click without hover (fact)
`Rollover` (`re/mac/decomp/Rollover.c`) has **no** `OnMouseDown`/`OnMouseUp`. It overrides only `Init` (0x34338: `xOffset`, `yOffset`, `xAbsolute`, `yAbsolute`, `contents`, `command`) and `OnMouseMove` (0x345b4). The command can only run through the popup that a mouse move creates: `OnMouseMove` builds a `PopupWindow` (top-left at pointer + offsets, `Reposition` 0x2e5a4), adopts it as a front child of the top modal, hands it `command`, and registers it as a mouse listener. `PopupWindow::OnMouseDown` sets `pressed`; `OnMouseUp` (0x2e6e0) kills the popup then runs the command if `pressed` (`popup-placement.md` 1). With no popup, a mouse down on a Rollover is not handled by it, so `TWindow::HandleEvent` passes it to whatever is behind it, then up to the parent chain; the command does **not** run.
So the engine (click without hover does nothing; hover then click works) matches the original. In the real game a click is always preceded by OS pointer motion, so the popup (placed exactly under the pointer when offsets are 0) catches the press; the Test Kitchen jars (`ui_kitchen.lua:250`, Reforged :440/:481) use default offsets. I found no synthetic mouse-move before a mouse-down in `TWindowManager::HandleEvent` (0x4ee4c; the event goes to the jump table by type; **inference** there is none, the jump targets were not decompiled).
**Engine action:** none required for fidelity. For real play on SDL, make sure a motion event is delivered before the button-down (touch-emulated clicks and some remote desktops send down without motion): the cheapest fix is to synthesise `onMouseMove(x,y)` immediately before a button-down whose position differs from the last known pointer position. This is a deliberate deviation. Test harnesses should send a move first. Popup hit testing with the 125 ms fade-in (`map-window.md`) is a separate question: whether a click during the fade lands is **unknown**.
